<a name="_52tjwnrpbjtv"></a>**Part 1 - Use the Event’x’.json files**

<a name="_9699m8j0572i"></a>**Level 1: The "Eyes on Glass" Phase**

**Story:** The time is 08:26 AM. As you are enjoying your first cup of coffee, multiple alerts appear on the dashboard. A huge block of bizarre text appears in the command line of a PowerShell process that has just started.

**Question 1: The Smoking Gun** Referencing **Event 4**, we have alerts firing on a Base64 encoded command. After decoding the string UwB0AGEAcgB0..., what does the actual payload reveal about the intent?

- A) It downloads a malicious payload using Net.WebClient, indicating a C2 connection.
- B) It executes a harmless Write-Output command, suggesting a test or demo.
- C) It attempts to encrypt files in the user's directory, indicating ransomware.
- D) It adds a hidden user to the local administrators group for persistence.

**Answer:** **B.**

- **The clues:** The -enc flag in Event 4 is followed by a specific Base64 string.
- **The decode:** If you decode the string, it translates to: Start-Process powershell.exe -ArgumentList 'Write-Output "Triage Smarter Not Harder"'
- **The verdict:** While the behavior (encoding commands) is suspicious, the payload is a harmless echo command.

<a name="_2r6ep29aij1a"></a>**Level 2: The "Connect the Dots" Phase**

**Story:** Although you have deciphered the command, you are still not convinced. To see how this process began, you zoom out. The lineage appears disorganized.

**Question 2: The Process Chain Anomaly** Looking at the process chain in **Events 3 and 4**, Wscript.exe spawns a new PowerShell.exe instance. Why is this specific parent-child relationship (WScript -> PowerShell) considered an important anomaly?

- A) Wscript.exe is a deprecated process that should never run on modern Windows.
- B) The process ID of the parent Wscript.exe is higher than the child process.
- C) It indicates a "Living off the Land" technique often used by intermediate loaders.
- D) PowerShell cannot technically be spawned by Wscript due to architecture limitations.

**Answer:** **C.**

- **The clues:** Legitimate users usually launch PowerShell from Explorer (Start Menu).
- **The rationale:** Malware authors often use .vbs or .js files (handled by Wscript) as "droppers" to break the detection chain before launching the real payload in PowerShell.
- **The verdict:** This chain is technically possible but operationally rare for a standard user, making it a high-fidelity pivot point for investigation.

![ref1]

<a name="_9erip9ayr0qe"></a>**Level 3: The "Panic Check" Phase**

**Story:** Your heart rate spikes as you see a new process spawn immediately after the PowerShell command in **Event 6**. Did the malware just establish persistence?

**Question 3: The False Positive Trap** Conhost.exe spawns immediately after the PowerShell activity with the flag -ForceV1. Based on the relationship between these processes, how should this event be classified?

- A) Malicious Persistence: The -ForceV1 flag indicates a registry hack.
- B) Suspicious Lateral Movement: Conhost.exe is likely tunneling RDP traffic.
- C) Normal OS Behavior: Conhost.exe is automatically spawned to host the interface for command-line apps.
- D) Privilege Escalation: Conhost.exe is running with higher system privileges than its parent.

**Answer:** **C.**

- **The clues:** The Parent PID of Conhost matches the PID of the PowerShell process.
- **The rationale:** Conhost.exe (Console Window Host) is the process Windows uses to draw the black window box you see when running command-line tools.
- **The verdict:** This is noise. Blocking Conhost would just break the user's ability to see their window.

![ref1]

<a name="_6roi0gqf2r5h"></a>**Level 4: The "Process Improvement" Phase**

**Story:** After the incident is closed, a junior analyst asks you: "If Base64 is used by hackers, why don't we just block it everywhere?"

**Question 4: The Administrative Reality** Why is relying solely on the presence of Base64 encoding (-enc) insufficient for automatically blocking a process or declaring an incident malicious?

- A) Base64 encoding is never used by legitimate software, so it is actually always safe to block.
- B) Legitimate administrators often use encoding to avoid syntax errors with special characters.
- C) The alert title is generated by AI and is known to be 50% inaccurate by default.
- D) Encoded commands are automatically blocked by the Windows Kernel anyway.

**Answer:** **B.**

- **The clues:** Look at tools like SCCM, Intune, or complicated Exchange scripts.
- **The rationale:** Sysadmins use Base64 to wrap complex scripts into a single block of text so they don't break when passed through command lines. It is a "dual-use" technique.
- **The verdict:** Blocking all Base64 would crash half of your IT department's management scripts.


<a name="_tvu9kwvuh1s"></a>**Part 2 - Use the .pcapng file**

<a name="_262dcjqwzviu"></a>**Level 1: Network Indicators**

**Question 1: The Malicious Infrastructure** - Referencing the JNDI injection string found in the User-Agent header of the initial GET request, what is the **exact IP address and port** of the malicious LDAP server the victim is being instructed to contact?

**Answer:** **192.168.3.5:1389**

**How to find it:**

1. **Locate the Request:** Look at **No. 6**, which shows the HTTP GET request to /Log4j-2.14.0-SNAPSHOT/api
1. **Inspect the User-Agent:** Find the string starting with ${jndi:ldap://
1. **Extract the IP:** The value immediately following the protocol ldap:// is 192.168.3.5:1389

![ref1]

<a name="_5vwo57tne1mt"></a>**Level 2: Payload Analysis**

**Question 2: The Staging Parameter** - In the same User-Agent string, the attacker passes a Base64 encoded payload to the LDAP server. What is the **exact name of the parameter** used to hold this Base64 string?

**Answer:** **pwshb64cmd**

**How to find it:**

1. **Analyze the LDAP Path:** In **No. 4**, look at the path following the IP address: /o=tomcat,pwshb64cmd=SQBmAC....
1. **Identify the Key-Value Pair:** The comma separates the organization (o=tomcat) from the next parameter
1. **Isolate the Key:** The text before the equals sign of the large Base64 block is pwshb64cmd. (This stands for "PowerShell Base64 Command")

![ref1]

<a name="_gqil3ie2qq9x"></a>**Level 3: Code Obfuscation**

**Question 3: The Decoded Process** - In the LDAP response, the attacker executes a command using JavaScript's String.fromCharCode function to bypass string-based detection. Decoding the decimal array 112,111,119,101,114..., what is the **exact executable file name** being launched?

**Answer:** **powershell.exe**

**How to find it:**

1. **Locate the Script:** In No. **19**, find the eval() function containing String.fromCharCode.
1. **Extract the ASCII Codes:** The first sequence is 112, 111, 119, 101, 114, 115, 104, 101, 108, 108, 46, 101, 120, 101.
1. **Decode:**
- 112 = p
- 111 = o
- 119 = w
- 101 = e
- 114 = r
- 115 = s
- 104 = h
- 101 = e
- 108 = l
- 108 = l
- 46 = .
- 101 = e
- 120 = x
- 101 = e
